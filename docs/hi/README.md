# burnrate

**पता लगाइए कि आपके कोडिंग एजेंट के टोकन असल में क्या जला रहा है — आपके अपने सेशन से मापा गया, कोई मार्केटिंग प्रतिशत नहीं।**

टोकन बचाने वाली हर skill एक आँकड़ा देती है। `65% बचत`। `बिल ~31% कम`। ये आँकड़े किसी और के सेशन से, किसी और की फ़ाइलों और आदतों से निकले हैं। ये आपके नहीं हैं, और आप इन्हें जाँच भी नहीं सकते।

तो अपने वाले जाँचिए। एक कमांड, कोई इंस्टॉल नहीं, कोई API key नहीं, कोई नेटवर्क नहीं:

```bash
python burnrate.py --all
```

---

## वह चीज़ जो कोई नहीं मापता

यह 348 सेशन का असली डेटा है — 36,000 मॉडल टर्न, 8.8 अरब टोकन:

| | कच्चे टोकन | हिस्सा | लागत-भारित हिस्सा |
|---|---:|---:|---:|
| **हर टर्न पर दोबारा भेजा गया कॉन्टेक्स्ट** (cache read) | 8,310,254,792 | **94.2%** | 49.6% |
| लिखा गया कॉन्टेक्स्ट (cache write) | 446,493,285 | 5.1% | 33.3% |
| **आउटपुट — जो एजेंट लिखता है** | 54,477,459 | **0.6%** | 16.3% |
| इनपुट (बिना कैश) | 13,730,167 | 0.2% | 0.8% |

**कॉन्टेक्स्ट: कच्चे टोकन का 99.2%, लागत-भारित 82.9%। आउटपुट: कच्चा 0.6%, भारित 16.3%।**

औसत (मध्यक) सेशन ने जितना लिखा, उससे **109 गुना ज़्यादा** कॉन्टेक्स्ट दोबारा भेजा। 348 सेशन में से केवल **5** ने दोबारा पढ़े गए से ज़्यादा लिखा।

जवाब छोटे करके, आर्टिकल हटाकर, या "गुफ़ा-मानव" की तरह बोलकर टोकन बचाने वाली हर skill उसी **0.6%** को ऑप्टिमाइज़ कर रही है। आउटपुट टोकन की ऊँची कीमत जोड़ भी लें, तब भी वह चार मदों में सबसे छोटी को निशाना बना रही है — और साथ ही अपने निर्देश उस कॉन्टेक्स्ट में जोड़ रही है जो हर टर्न पर दोबारा भेजा जाता है। हमेशा के लिए।

इसीलिए बचत कभी सामने आती ही नहीं।

*(दोनों हिस्से इसलिए दिखाए गए हैं क्योंकि वे अलग-अलग कहानी कहते हैं। कच्चा हिस्सा वह है जो आपकी कॉन्टेक्स्ट विंडो भरता है; भारित हिस्सा प्रकाशित बिलिंग अनुपात इस्तेमाल करता है — cache write 1.25×, cache read 0.10×, आउटपुट इनपुट का 5×। सिर्फ़ अपने पक्ष वाला आँकड़ा उद्धृत करना ही असली समस्या है, समाधान नहीं।)*

## इसे अपने आँकड़ों पर चलाइए

```bash
git clone https://github.com/xniperbuilds/burnrate
cd burnrate/plugins/burnrate/skills/burnrate/scripts
python burnrate.py --days 30
```

Python 3.8+, केवल स्टैण्डर्ड लाइब्रेरी — कोई `pip install` नहीं, कोई Node नहीं, कोई shell इंस्टॉलर नहीं, कोई `curl | bash` नहीं। Windows, macOS और Linux — तीनों पर एक जैसा चलता है।

यह आपकी डिस्क पर पहले से मौजूद सेशन ट्रांसक्रिप्ट (`~/.claude/projects/**/*.jsonl`) पढ़ता है और बताता है:

- आपका कच्चा और भारित टोकन विभाजन
- कौन-से टूल आपके कॉन्टेक्स्ट में सबसे ज़्यादा सामग्री डालते हैं, और उनके नतीजों का औसत आकार
- कौन-सी फ़ाइलें आप बार-बार पढ़ते हैं
- कौन-सी फ़ाइलें इतनी बड़ी हैं कि अकेले पूरे सेशन पर हावी हो जाएँ
- इमेज और बाइनरी पेलोड — अलग से और ईमानदारी से गिने गए

```
  [HIGH] 94 फ़ाइलें 5+ बार पढ़ी गईं
      वही अपरिवर्तित फ़ाइलें दोबारा पढ़ने पर पहली बार के अलावा लगभग
      24 लाख टोकन लगे (अनुमानित)। सबसे ख़राब:
      project-notes.md (107 बार)।
      -> ये इसलिए दोबारा पढ़ी जाती हैं क्योंकि इनकी सामग्री कॉन्टेक्स्ट में टिकी नहीं।

  [HIGH] कॉन्टेक्स्ट में वापस आने वाली हर चीज़ का 50% Read से आता है
      3,100 कॉल ने कुल ~45 लाख टोकन लौटाए; प्रति कॉल औसत 1,400 टोकन,
      अकेला सबसे बड़ा नतीजा ~16,800 टोकन।
      -> पूरी फ़ाइल के बजाय offset/limit से पढ़िए।
```

## आपके कुछ टाइप करने से पहले क्या लोड होता है

```bash
python burnrate.py --startup
```

स्टार्टअप कॉन्टेक्स्ट **हर सेशन के हर टर्न** पर चुकाया जाता है, इसलिए यह जानने लायक सबसे असरदार चीज़ है। असली आउटपुट:

```
-- मापा गया (हर सेशन का पहला बिल होने वाला टर्न) ----------------
  स्टार्टअप कॉन्टेक्स्ट (मध्यक)    60,057 टोकन   310 सेशन में
  यह आगे के हर टर्न पर cache_read के रूप में दोबारा भेजा जाता है।

-- जिम्मेदारी तय (आपके कॉन्फ़िग से स्कैन, अनुमानित) --------------
  skill descriptions                    8,185  57 skill
  CLAUDE.md (यूज़र)                      3,674
  मेमोरी इंडेक्स (MEMORY.md)             2,758  सीमा 200 पंक्तियाँ / 25KB
  सब-एजेंट descriptions                  1,258  18 एजेंट
  कुल तय किया गया                       15,875

  शेष जिसकी जिम्मेदारी तय नहीं          44,182  सिस्टम प्रॉम्प्ट + टूल स्कीमा
  आपका हिस्सा                             26.4%  यही आप घटा सकते हैं
```

तीन बातें इसे कॉन्फ़िग-फ़ाइल अनुमान लगाने वाले टूल से अलग करती हैं:

- **मापा गया** आँकड़ा सटीक है — यह शब्द गिनने से नहीं, `usage` फ़ील्ड से आता है।
- **शेष** को छिपाया नहीं, बताया जाता है। उस स्टार्टअप लागत का दो-तिहाई सिस्टम प्रॉम्प्ट और टूल स्कीमा है, जो आपकी फ़ाइलें कितनी भी संपादित कर लें, बदलेगा नहीं। यह बताना आपको उस आँकड़े को ऑप्टिमाइज़ करने से बचाता है जिसे आप हिला ही नहीं सकते।
- skill और एजेंट के लिए **केवल frontmatter गिना जाता है**। उनका मुख्य भाग ज़रूरत पड़ने पर लोड होता है, इसलिए पूरी skill फ़ाइल गिनना — जैसा कॉन्फ़िग डायरेक्टरी स्कैन करने वाले टूल अक्सर करते हैं — स्टार्टअप लागत को कई गुना बढ़ा-चढ़ाकर दिखाता है।

आम हैरानी: **इंस्टॉल की हुई पर इस्तेमाल न होने वाली skills `CLAUDE.md` से भारी पड़ती हैं।** हर skill का description हर टर्न पर लोड होता है, चाहे आप उसे बुलाएँ या नहीं — इसीलिए `--startup` आपके पूरे इतिहास में असली `Skill` टूल कॉल भी गिनता है और *इंस्टॉल* को *इस्तेमाल* से अलग करता है:

```
  आपके पूरे इतिहास में (416 ट्रांसक्रिप्ट, --days विंडो नहीं):
    इंस्टॉल 57  |  जिनकी कॉल दर्ज है 12  |  जिनकी नहीं 45

  हर टर्न ~6,143 टोकन उन skills पर जाता है जिनकी कोई कॉल दर्ज नहीं।
  100 टर्न के सेशन में यह लगभग 6.1 लाख है।
```

यह बर्बादी का अनुमान नहीं है — यह नाम सहित बर्बादी है, सबसे भारी से क्रम में। सिर्फ़ कॉन्फ़िग डायरेक्टरी स्कैन करने वाला टूल यह जान ही नहीं सकता।

## अपनी बचत खुद साबित कीजिए

```bash
python burnrate.py --snapshot before
#  ... कुछ बदलिए ...
python burnrate.py --compare before
```

`--compare` **प्रति-टर्न औसत** बताता है, ताकि ज़्यादा व्यस्त हफ़्ता गिरावट का भेस न बना ले:

```
                                            पहले        अब      बदलाव
  cache write (नया कॉन्टेक्स्ट)               8.6K       5.9K    -31.7%
  cache read (हर टर्न दोबारा भेजा)           213.3K     219.5K      2.9%
  आउटपुट (जो एजेंट ने लिखा)                    1.4K       1.4K      1.3%

  लागत-भारित, प्रति टर्न                      39.1K      36.4K     -6.9%

  यह आपका मापा हुआ बदलाव है। यह किसी और के बारे में दावा नहीं है।
```

## skill के रूप में इंस्टॉल करें

```
/plugin marketplace add xniperbuilds/burnrate
/plugin install burnrate@xniperbuilds
```

इंस्टॉल होने पर यह तीन काम करता है: सुझाव देने से पहले मापता है; सस्ते 0.6% के बजाय महँगे 83–99% को निशाना बनाने वाला कॉन्टेक्स्ट अनुशासन लागू करता है; और दोबारा मापता है ताकि सुधार दावा नहीं, तथ्य हो। कटौती की पूरी सूची — असर के क्रम में, हर कटौती की कीमत के साथ — [`references/cuts.md`](../../plugins/burnrate/skills/burnrate/references/cuts.md) में है।

## यह क्या नहीं करेगा

- **आपके एजेंट को अजीब तरह से बोलने पर मजबूर नहीं करेगा।** तार-जैसी संक्षिप्त भाषा बिल का छोटा-सा हिस्सा घटाती है और नतीजों की समीक्षा कठिन बना देती है।
- **आपको कोई औसत नहीं देगा।** केवल आपके मापे हुए आँकड़े।
- **अपनी लागत नहीं छिपाएगा।** बुलाए जाने पर यह skill फ़ाइल भी कॉन्टेक्स्ट में जाती है। छोटे सेशन में यह अतिरिक्त बोझ बचत से ज़्यादा हो सकता है — और `--compare` आपको यह ईमानदारी से दिखाएगा।
- **शुद्धता को टोकन के बदले नहीं बेचेगा।** संक्षिप्तता केवल भेजी जाने वाली सामग्री पर लागू होती है — तर्क, टेस्ट, या कोड और एरर के मूल पाठ पर कभी नहीं।

## ज्ञात सीमाएँ

- टोकन के कुल आँकड़े `usage` फ़ील्ड से आते हैं और सटीक हैं। टूल के नतीजों की मात्रा ~4 अक्षर/टोकन के हिसाब से बदली जाती है और जहाँ भी आती है, अनुमानित बताई जाती है।
- इमेज और PDF अक्षरों से नहीं, अपने आयामों से बिल होते हैं। इन्हें अलग गिना जाता है और कभी टोकन संख्या में नहीं बदला जाता।
- लागत-भार टोकन श्रेणियों के बीच प्रकाशित अनुपात इस्तेमाल करता है, किसी मॉडल-विशेष कीमत का नहीं — इसलिए भारित कॉलम एक हिस्सा है, रकम नहीं।
- सब्सक्रिप्शन प्लान उपयोग को API कीमत से अलग तरह से तौल सकते हैं। इसीलिए दोनों हिस्से बताए जाते हैं; किसी को भी बिल के रूप में पेश नहीं किया जाता।
- यह केवल स्थानीय ट्रांसक्रिप्ट देखता है। किसी दूसरी मशीन या ब्राउज़र में किया गया काम नहीं गिना जाता।
- ऊपर का डेटा एक भारी उपयोगकर्ता के 348 सेशन का है। यह प्रमाण है, कोई सार्वभौमिक नियम नहीं — और यही तो पूरी बात है। इसे अपने डेटा पर चलाइए।
