# burnrate

**查清楚到底是什么在烧掉你的编码智能体 token —— 用你自己会话的实测数据，而不是一个营销百分比。**

每一个"节省 token"的技能都会给你一个数字。`节省 65%`。`账单降低约 31%`。这些数字来自别人的会话、别人的文件、别人的习惯。它们不是你的，而且你无法核实。

所以，核实你自己的。一条命令，无需安装、无需 API key、无需联网：

```bash
python burnrate.py --all
```

---

## 没有人测量的那件事

这是一份真实的 348 个会话的数据 —— 36,000 个模型回合，88 亿 token：

| | 原始 token | 占比 | 按成本加权占比 |
|---|---:|---:|---:|
| **每回合重发的上下文**（cache read） | 8,310,254,792 | **94.2%** | 49.6% |
| 写入的上下文（cache write） | 446,493,285 | 5.1% | 33.3% |
| **输出 —— 智能体写出来的内容** | 54,477,459 | **0.6%** | 16.3% |
| 输入（未缓存） | 13,730,167 | 0.2% | 0.8% |

**上下文：占原始 token 的 99.2%，按成本加权占 82.9%。输出：原始 0.6%，加权 16.3%。**

中位数会话重发的上下文是它写出内容的 **109 倍**。348 个会话中，只有 **5 个**写的比重发的多。

任何靠缩短回复、去掉冠词、或者用"原始人语言"说话来省 token 的技能，优化的都是那 **0.6%**。即使按输出 token 更高的单价加权，它针对的仍然是四项里最小的一项 —— 与此同时，它自己的指令还被加进了每回合都要重发的上下文里，永远如此。

这就是为什么那些节省从来没真正出现过。

*（原始占比和加权占比都列出来，因为它们讲的是两个不同的故事。原始占比是塞满你上下文窗口的东西；加权用的是公开的计费比例 —— cache write 1.25 倍、cache read 0.10 倍、输出 5 倍于输入。只挑对自己有利的那个来说，正是问题本身，而不是解法。）*

## 在你自己的数据上运行

```bash
git clone https://github.com/xniperbuilds/burnrate
cd burnrate/plugins/burnrate/skills/burnrate/scripts
python burnrate.py --days 30
```

Python 3.8+，仅使用标准库 —— 无需 pip install、无需 Node、无需 shell 安装脚本、没有 `curl | bash`。在 Windows、macOS 和 Linux 上表现一致。

它读取你磁盘上已有的会话记录（`~/.claude/projects/**/*.jsonl`），然后输出：

- 你的原始与加权 token 构成
- 哪些工具往你的上下文里塞进了最多内容，以及它们的平均结果大小
- 你反复读取的是哪些文件
- 哪些文件大到足以独自主导一个会话
- 图片与二进制负载，单独统计，并且诚实标注

```
  [HIGH] 94 个文件被读取 5 次以上
      重复读取这些未改动的文件，在首次读取之外大约多花了 240 万 token
      （近似值）。最严重的：project-notes.md（107 次）。
      -> 它们被反复读取，是因为其内容没能留在上下文里。

  [HIGH] Read 占了所有回灌进上下文内容的 50%
      3,100 次调用共返回约 450 万 token；平均每次调用 1,400 token，
      单次最大结果约 16,800 token。
      -> 用 offset/limit 读取，而不是整个文件。
```

## 你敲第一个字之前，已经加载了什么

```bash
python burnrate.py --startup
```

启动上下文在**每个会话的每一个回合**都要付费，所以它是最值得先弄清楚的东西。真实输出：

```
-- 实测（每个会话第一个计费回合）--------------------------------
  启动上下文中位数            60,057 token   来自 310 个会话
  它会作为 cache_read 在此后每一个回合重新发送。

-- 归因（扫描你的配置，近似值）----------------------------------
  技能描述                              8,185  57 个技能
  CLAUDE.md（用户级）                    3,674
  记忆索引（MEMORY.md）                  2,758  上限 200 行 / 25KB
  子智能体描述                           1,258  18 个
  归因合计                              15,875

  未归因残差                            44,182  系统提示词 + 工具 schema
  你可控的份额                            26.4%
```

有三点让它不同于一个配置文件估算器：

- **实测**数字是精确的 —— 来自 `usage` 字段，不是数单词数出来的。
- **残差**是被报告出来的，而不是藏起来的。启动开销里有三分之二是系统提示词和工具 schema，无论你怎么改自己的文件都不会变。告诉你这一点，是为了让你不去优化一个你根本推不动的数字。
- 对技能和子智能体**只统计 frontmatter**。它们的正文是按需加载的，所以把整个技能文件都算进去 —— 那些扫描配置目录的工具往往就是这么干的 —— 会把启动开销高估好几倍。

常见的意外发现：**装了但从不用的技能，比 `CLAUDE.md` 还重。** 每个技能的描述无论你是否调用都会在每回合加载 —— 所以 `--startup` 还会统计你全部历史中真实的 `Skill` 调用次数，把「已安装」和「真用过」分开：

```
  在你的全部历史中（416 份会话记录，不是 --days 窗口）：
    已安装 57  |  有调用记录 12  |  无调用记录 45

  每回合约有 6,143 token 花在没有任何调用记录的技能上。
  一个 100 回合的会话大约就是 61 万。
```

这不是对浪费的估算 —— 这是有名有姓的浪费，按从重到轻列出。只扫描配置目录的工具不可能知道这一点。

## 证明你自己的节省

```bash
python burnrate.py --snapshot before
#  ... 做出改动 ...
python burnrate.py --compare before
```

`--compare` 报告的是**每回合平均值**，所以更忙的一周不会伪装成性能倒退：

```
                                             之前        现在      变化
  cache write（新上下文）                     8.6K       5.9K    -31.7%
  cache read（每回合重发的上下文）           213.3K     219.5K      2.9%
  output（智能体写出的内容）                   1.4K       1.4K      1.3%

  按成本加权的每回合用量                      39.1K      36.4K     -6.9%

  这是你实测到的变化。它不是关于任何其他人的说法。
```

## 作为技能安装

```
/plugin marketplace add xniperbuilds/burnrate
/plugin install burnrate@xniperbuilds
```

装好之后它做三件事：先测量再建议；施加针对昂贵的那 83–99%（而不是便宜的 0.6%）的上下文纪律；然后再测一次，让改进成为事实。完整的削减手册 —— 按影响排序，并写明每项削减的代价 —— 在 [`references/cuts.md`](../../plugins/burnrate/skills/burnrate/references/cuts.md)。

## 它不会做的事

- **不会让你的智能体说话怪腔怪调。** 电报式输出削减的是账单里很小的一块，却让结果更难审阅。
- **不会给你一个平均值。** 只给你实测的数字。
- **不会隐藏它自身的开销。** 被调用时这个技能文件也会进入上下文。在短会话里这份开销可能超过它省下的量 —— 而 `--compare` 会如实告诉你。
- **不会拿正确性换 token。** 简洁只适用于传输的内容，绝不适用于推理、测试、以及代码和报错的原文。

## 已知局限

- Token 总量来自 `usage` 字段，是精确的。工具结果的体量按约 4 字符/token 换算，凡出现之处都标注为近似值。
- 图片和 PDF 按尺寸计费，而非字符数。它们被单独统计，绝不换算成 token 数字。
- 成本加权用的是各类 token 之间的公开比例，而不是各模型的具体价格 —— 所以加权那一列是占比，不是货币金额。
- 订阅制套餐对用量的加权方式可能与 API 定价不同。正因如此，原始占比和加权占比都会报告；两者都不作为账单呈现。
- 只能看到本地会话记录。在另一台机器上或浏览器里做的工作不会被计入。
- 上面那份语料是某一位重度用户的 348 个会话。它是证据，不是普适定律 —— 而这正是重点。在你自己的数据上跑一遍。
