# burnrate

**查清楚到底是什麼在燒掉你的程式碼代理 token —— 用你自己工作階段的實測數據，而不是一個行銷百分比。**

每一個「節省 token」的技能都會給你一個數字。`節省 65%`。`帳單降低約 31%`。這些數字來自別人的工作階段、別人的檔案、別人的習慣。它們不是你的，而且你無法查證。

所以，查證你自己的。一行指令，不用安裝、不用 API key、不用連網：

```bash
python burnrate.py --all
```

---

## 沒有人量測的那件事

這是一份真實的 348 個工作階段的資料 —— 36,000 個模型回合，88 億 token：

| | 原始 token | 佔比 | 依成本加權佔比 |
|---|---:|---:|---:|
| **每回合重送的脈絡**（cache read） | 8,310,254,792 | **94.2%** | 49.6% |
| 寫入的脈絡（cache write） | 446,493,285 | 5.1% | 33.3% |
| **輸出 —— 代理寫出來的內容** | 54,477,459 | **0.6%** | 16.3% |
| 輸入（未快取） | 13,730,167 | 0.2% | 0.8% |

**脈絡：佔原始 token 的 99.2%，依成本加權佔 82.9%。輸出：原始 0.6%，加權 16.3%。**

中位數的工作階段重送的脈絡是它寫出內容的 **109 倍**。348 個工作階段中，只有 **5 個**寫的比重送的多。

任何靠縮短回覆、拿掉冠詞，或用「原始人語氣」說話來省 token 的技能，最佳化的都是那 **0.6%**。就算把輸出 token 較高的單價算進去，它針對的仍然是四項裡最小的一項 —— 與此同時，它自己的指令還被加進每回合都要重送的脈絡裡，而且是永久的。

這就是為什麼那些節省從來沒真正出現過。

*（原始佔比與加權佔比都列出來，因為兩者講的是不同的故事。原始佔比是塞滿你脈絡視窗的東西；加權則採用公開的計費比例 —— cache write 1.25 倍、cache read 0.10 倍、輸出 5 倍於輸入。只挑對自己有利的那個來講，正是問題本身，而不是解法。）*

## 在你自己的資料上執行

```bash
git clone https://github.com/xniperbuilds/burnrate
cd burnrate/plugins/burnrate/skills/burnrate/scripts
python burnrate.py --days 30
```

Python 3.8+，只用標準函式庫 —— 不用 pip install、不用 Node、沒有 shell 安裝腳本、沒有 `curl | bash`。在 Windows、macOS 與 Linux 上表現一致。

它讀取你硬碟上既有的工作階段記錄（`~/.claude/projects/**/*.jsonl`），然後輸出：

- 你的原始與加權 token 組成
- 哪些工具往你的脈絡裡塞進最多內容，以及它們的平均結果大小
- 你反覆讀取的是哪些檔案
- 哪些檔案大到足以單獨主宰一個工作階段
- 圖片與二進位負載，單獨統計，並且誠實標註

```
  [HIGH] 94 個檔案被讀取 5 次以上
      重複讀取這些未變動的檔案，在首次讀取之外大約多花了 240 萬 token
      （概估）。最嚴重的：project-notes.md（107 次）。
      -> 它們被反覆讀取，是因為內容沒能留在脈絡裡。

  [HIGH] Read 佔了所有回灌進脈絡內容的 50%
      3,100 次呼叫共回傳約 450 萬 token；平均每次呼叫 1,400 token，
      單次最大結果約 16,800 token。
      -> 用 offset/limit 讀取，而不是整個檔案。
```

## 你打第一個字之前，已經載入了什麼

```bash
python burnrate.py --startup
```

啟動脈絡在**每個工作階段的每一個回合**都要付費，所以它是最值得先弄清楚的東西。實際輸出：

```
-- 實測（每個工作階段第一個計費回合）----------------------------
  啟動脈絡中位數              60,057 token   來自 310 個工作階段
  它會作為 cache_read 在此後每一個回合重新送出。

-- 歸因（掃描你的設定，概估）------------------------------------
  技能描述                              12,998  105 個技能
  CLAUDE.md（使用者層級）                3,674
  記憶索引（MEMORY.md）                  2,718  上限 200 行 / 25KB
  子代理描述                             1,258  18 個
  歸因合計                              20,648

  未歸因殘差                            39,409  系統提示詞 + 工具 schema
  你可控的比例                            34.4%
```

有三點讓它不同於一個設定檔估算工具：

- **實測**數字是精確的 —— 來自 `usage` 欄位，不是數單字數出來的。
- **殘差**是被報告出來的，而不是藏起來。啟動開銷裡有三分之二是系統提示詞與工具 schema，不管你怎麼改自己的檔案都不會變。告訴你這一點，是為了不讓你去最佳化一個你根本推不動的數字。
- 對技能與子代理**只統計 frontmatter**。它們的內文是按需載入的，所以把整個技能檔案都算進去 —— 那些掃描設定目錄的工具往往就是這麼做 —— 會把啟動開銷高估好幾倍。

常見的意外發現：**裝了卻從不用的技能，比 `CLAUDE.md` 還重。** 每個技能的描述無論你是否呼叫都會在每回合載入 —— 所以 `--startup` 還會統計你全部歷史中真實的 `Skill` 呼叫次數，把「已安裝」和「真的用過」分開：

```
  在你的全部歷史中（416 份工作階段記錄，不是 --days 視窗）：
    已安裝 105  |  有呼叫記錄 12  |  無呼叫記錄 93

  每回合約有 10,956 token 花在沒有任何呼叫記錄的技能上。
  一個 100 回合的工作階段大約就是 110 萬。
```

這不是對浪費的估算 —— 這是有名有姓的浪費，依由重到輕列出。只掃描設定目錄的工具不可能知道這件事。

## 證明你自己的節省

```bash
python burnrate.py --snapshot before
#  ... 做出變更 ...
python burnrate.py --compare before
```

`--compare` 回報的是**每回合平均值**，所以更忙的一週不會偽裝成效能倒退：

```
                                             之前        現在      變化
  cache write（新脈絡）                       8.6K       5.9K    -31.7%
  cache read（每回合重送）                   213.3K     219.5K      2.9%
  output（代理寫出的內容）                     1.4K       1.4K      1.3%

  依成本加權的每回合用量                      39.1K      36.4K     -6.9%

  這是你實測到的變化。它不是關於任何其他人的說法。
```

## 安裝為技能

```
/plugin marketplace add xniperbuilds/burnrate
/plugin install burnrate@xniperbuilds
```

裝好之後它做三件事：先量測再建議；施加針對昂貴的那 83–99%（而不是便宜的 0.6%）的脈絡紀律；然後再量一次，讓改善成為事實。完整的削減手冊 —— 依影響排序，並寫明每項削減的代價 —— 在 [`references/cuts.md`](../../plugins/burnrate/skills/burnrate/references/cuts.md)。

## 它不會做的事

- **不會讓你的代理說話怪腔怪調。** 電報式輸出削減的是帳單裡很小的一塊，卻讓結果更難審閱。
- **不會給你一個平均值。** 只給你實測的數字。
- **不會隱藏它自身的開銷。** 被呼叫時這個技能檔案也會進入脈絡。在短工作階段裡這份開銷可能超過它省下的量 —— 而 `--compare` 會如實告訴你。
- **不會拿正確性換 token。** 精簡只適用於傳輸的內容，絕不適用於推理、測試，以及程式碼和錯誤訊息的原文。

## 已知限制

- Token 總量來自 `usage` 欄位，是精確的。工具結果的量體按約 4 字元/token 換算，凡出現之處都標註為概估值。
- 圖片與 PDF 按尺寸計費，而非字元數。它們被單獨統計，絕不換算成 token 數字。
- 成本加權採用各類 token 之間的公開比例，而非各模型的實際價格 —— 所以加權那一欄是佔比，不是金額。
- 訂閱制方案對用量的加權方式可能與 API 定價不同。正因如此，原始佔比與加權佔比都會報告；兩者都不作為帳單呈現。
- 只能看到本機的工作階段記錄。在另一台機器上或瀏覽器裡做的工作不會被計入。
- 上面那份語料是某一位重度使用者的 348 個工作階段。它是證據，不是普世定律 —— 而這正是重點。在你自己的資料上跑一遍。
