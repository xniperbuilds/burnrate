# burnrate

**코딩 에이전트의 토큰을 실제로 무엇이 태우고 있는지 알아내세요 — 마케팅용 퍼센트가 아니라, 당신 자신의 세션에서 측정한 값으로.**

토큰을 아껴준다는 스킬은 모두 숫자를 약속합니다. `65% 절감`. `청구액 약 31% 감소`. 그 숫자들은 다른 사람의 세션, 다른 사람의 파일, 다른 사람의 습관에서 나온 것입니다. 당신의 것이 아니고, 확인할 수도 없습니다.

그러니 당신 것을 확인하세요. 명령어 하나, 설치 없음, API 키 없음, 네트워크 없음:

```bash
python burnrate.py --all
```

---

## 아무도 측정하지 않는 것

실제 348개 세션 데이터입니다 — 모델 턴 36,000회, 토큰 88억 개:

| | 원시 토큰 | 비율 | 비용 가중 비율 |
|---|---:|---:|---:|
| **매 턴 다시 전송되는 컨텍스트**(cache read) | 8,310,254,792 | **94.2%** | 49.6% |
| 기록된 컨텍스트(cache write) | 446,493,285 | 5.1% | 33.3% |
| **출력 — 에이전트가 쓰는 것** | 54,477,459 | **0.6%** | 16.3% |
| 입력(캐시 안 됨) | 13,730,167 | 0.2% | 0.8% |

**컨텍스트: 원시 토큰의 99.2%, 비용 가중 82.9%. 출력: 원시 0.6%, 가중 16.3%.**

중앙값 세션은 자신이 쓴 양의 **109배**에 달하는 컨텍스트를 다시 보냈습니다. 348개 세션 중 쓴 양이 재전송량보다 많았던 것은 단 **5개**입니다.

답변을 줄이거나, 관사를 빼거나, 원시인처럼 말해서 토큰을 아끼는 스킬은 전부 그 **0.6%**를 최적화하고 있습니다. 출력 토큰의 단가가 더 높다는 점을 감안해도, 네 항목 중 가장 작은 것을 노리는 셈입니다 — 그러면서 자신의 지시문은 매 턴 다시 전송되는 컨텍스트에 영원히 더해집니다.

절감 효과가 좀처럼 나타나지 않는 이유가 바로 이것입니다.

*(원시 비율과 가중 비율을 모두 보여주는 이유는 둘이 서로 다른 이야기를 하기 때문입니다. 원시는 컨텍스트 창을 채우는 것이고, 가중은 공개된 과금 비율 — cache write 1.25배, cache read 0.10배, 출력은 입력의 5배 — 을 적용한 것입니다. 유리한 쪽만 인용하는 것이야말로 문제이지 해법이 아닙니다.)*

## 당신의 숫자로 실행하기

```bash
git clone https://github.com/xniperbuilds/burnrate
cd burnrate/plugins/burnrate/skills/burnrate/scripts
python burnrate.py --days 30
```

Python 3.8+, 표준 라이브러리만 사용 — pip install 없음, Node 없음, 셸 설치 스크립트 없음, `curl | bash` 없음. Windows, macOS, Linux에서 동일하게 동작합니다.

이미 디스크에 있는 세션 기록(`~/.claude/projects/**/*.jsonl`)을 읽고 다음을 출력합니다:

- 원시 및 가중 토큰 구성
- 어떤 도구가 컨텍스트에 가장 많은 분량을 넣는지, 그 평균 결과 크기
- 반복해서 읽고 있는 파일
- 혼자서 한 세션을 지배할 만큼 큰 파일
- 이미지와 바이너리 페이로드(별도 집계, 정직한 처리)

```
  [HIGH] 5회 이상 읽힌 파일 94개
      변경되지 않은 같은 파일을 다시 읽는 데 최초 읽기 이후로 약
      240만 토큰(근사치). 최악: project-notes.md (107회).
      -> 내용이 컨텍스트에 남지 못해 반복해서 읽히고 있습니다.

  [HIGH] 컨텍스트로 되돌아오는 전체 분량의 50%가 Read
      3,100회 호출로 총 약 450만 토큰. 호출당 평균 1,400 토큰,
      단일 결과 최대 약 16,800 토큰.
      -> 파일 전체가 아니라 offset/limit으로 읽으세요.
```

## 무언가를 입력하기 전에 무엇이 로드되는가

```bash
python burnrate.py --startup
```

시작 컨텍스트는 **모든 세션의 모든 턴**에서 과금되므로, 가장 먼저 알아야 할 지렛대입니다. 실제 출력:

```
-- 측정값 (각 세션의 첫 과금 턴) --------------------------------
  시작 컨텍스트 중앙값            60,057 토큰   310개 세션
  이후 모든 턴에서 cache_read로 다시 전송됩니다.

-- 귀속 (설정 스캔, 근사치) -------------------------------------
  스킬 description                      12,998  스킬 105개
  CLAUDE.md (사용자)                     3,674
  메모리 인덱스 (MEMORY.md)              2,718  최대 200줄 / 25KB
  서브에이전트 description               1,258  18개
  귀속 합계                             20,648

  귀속 불가 잔여                        39,409  시스템 프롬프트 + 도구 schema
  당신이 줄일 수 있는 비중                34.4%
```

설정 파일 추정기와 다른 점이 세 가지 있습니다:

- **측정값**은 정확합니다 — 단어 수 추정이 아니라 `usage` 필드에서 가져옵니다.
- **잔여값**을 숨기지 않고 보고합니다. 시작 비용의 3분의 2는 시스템 프롬프트와 도구 schema이며, 당신의 파일을 아무리 고쳐도 바뀌지 않습니다. 이를 알려주는 건 움직일 수 없는 숫자를 최적화하지 않게 하기 위해서입니다.
- 스킬과 서브에이전트는 **frontmatter만 계산**합니다. 본문은 필요할 때 로드되므로, 스킬 파일 전체를 세면 — 설정 디렉터리를 스캔하는 도구들이 흔히 그러듯 — 시작 비용을 몇 배로 과대평가하게 됩니다.

흔한 놀라움: **설치해두고 쓰지 않는 스킬이 `CLAUDE.md`보다 무겁습니다.** 각 스킬의 description은 호출 여부와 관계없이 매 턴 로드됩니다. 그래서 `--startup`은 전체 기록에서 실제 `Skill` 도구 호출을 세어 *설치됨*과 *사용됨*을 구분합니다:

```
  전체 기록 기준 (416개 기록, --days 창이 아님):
    설치 105  |  호출 기록 있음 12  |  호출 기록 없음 93

  호출 기록이 없는 스킬에 매 턴 약 10,956 토큰이 나갑니다.
  100턴 세션이면 약 110만 토큰입니다.
```

이것은 낭비의 추정치가 아니라 이름이 붙은 낭비이며, 무거운 순으로 나열됩니다. 설정 디렉터리만 스캔하는 도구는 이걸 알 수 없습니다.

## 당신의 절감을 증명하기

```bash
python burnrate.py --snapshot before
#  ... 무언가를 바꾸고 ...
python burnrate.py --compare before
```

`--compare`는 **턴당 평균**을 보고하므로, 더 바빴던 한 주가 퇴보처럼 보이지 않습니다:

```
                                             이전        현재      변화
  cache write (새 컨텍스트)                   8.6K       5.9K    -31.7%
  cache read (매 턴 재전송)                  213.3K     219.5K      2.9%
  output (에이전트가 쓴 것)                    1.4K       1.4K      1.3%

  비용 가중 / 턴                             39.1K      36.4K     -6.9%

  이것은 당신이 측정한 변화입니다. 다른 누구에 대한 주장이 아닙니다.
```

## 스킬로 설치하기

```
/plugin marketplace add xniperbuilds/burnrate
/plugin install burnrate@xniperbuilds
```

설치하면 세 가지를 합니다: 제안하기 전에 먼저 측정하고, 값싼 0.6%가 아니라 비싼 83~99%를 겨냥한 컨텍스트 규율을 적용하며, 다시 측정해 개선을 주장이 아닌 사실로 만듭니다. 전체 절감 플레이북 — 효과순 정렬, 각 절감의 대가 명시 — 은 [`references/cuts.md`](../../plugins/burnrate/skills/burnrate/references/cuts.md)에 있습니다.

## 하지 않는 것

- **에이전트가 이상하게 말하게 만들지 않습니다.** 전보식 출력은 청구액의 아주 작은 부분만 줄이면서 결과 검토를 어렵게 만듭니다.
- **평균값을 제시하지 않습니다.** 당신의 측정값만 제시합니다.
- **자신의 비용을 숨기지 않습니다.** 호출되면 이 스킬 파일도 컨텍스트에 들어갑니다. 짧은 세션에서는 그 오버헤드가 절감분을 넘을 수 있고, `--compare`가 이를 정직하게 보여줍니다.
- **정확성을 토큰과 바꾸지 않습니다.** 간결함은 전송되는 내용에만 적용되며, 추론·테스트·코드와 오류 원문에는 결코 적용되지 않습니다.

## 알려진 한계

- 토큰 총량은 `usage` 필드에서 나온 정확한 값입니다. 도구 결과 분량은 약 4자/토큰으로 환산하며, 등장하는 모든 곳에 근사치로 표기됩니다.
- 이미지와 PDF는 문자 수가 아니라 크기(치수)로 과금됩니다. 별도로 집계하며 토큰 수로 변환하지 않습니다.
- 비용 가중은 토큰 종류 간 공개 비율이지 모델별 가격이 아닙니다 — 따라서 가중 열은 비율이지 금액이 아닙니다.
- 구독 요금제는 API 가격과 다르게 가중할 수 있습니다. 그래서 원시와 가중을 모두 보고하며, 어느 쪽도 청구서로 제시하지 않습니다.
- 로컬 세션 기록만 볼 수 있습니다. 다른 기기나 브라우저에서 한 작업은 집계되지 않습니다.
- 위 데이터는 한 헤비 유저의 348개 세션입니다. 보편 법칙이 아니라 증거입니다 — 그리고 그게 핵심입니다. 당신의 데이터로 실행해 보세요.
