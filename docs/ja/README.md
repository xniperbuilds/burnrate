# burnrate

**コーディングエージェントのトークンを実際に何が食いつぶしているのかを突き止める。マーケティング上の割合ではなく、自分のセッションから実測した数字で。**

トークン節約系のスキルはどれも数字を約束します。`65% 削減`。`請求が約 31% 減`。それらの数字は他人のセッション、他人のファイル、他人の習慣から出たものです。あなたのものではないし、検証もできません。

だから自分のを検証しましょう。コマンド 1 つ、インストール不要、API キー不要、ネットワーク不要：

```bash
python burnrate.py --all
```

---

## 誰も測っていないこと

実際の 348 セッション分のデータです ── モデルターン 36,000 回、トークン 88 億：

| | 生のトークン | 割合 | コスト加重での割合 |
|---|---:|---:|---:|
| **毎ターン再送されるコンテキスト**（cache read） | 8,310,254,792 | **94.2%** | 49.6% |
| 書き込まれたコンテキスト（cache write） | 446,493,285 | 5.1% | 33.3% |
| **出力 ── エージェントが書くもの** | 54,477,459 | **0.6%** | 16.3% |
| 入力（キャッシュなし） | 13,730,167 | 0.2% | 0.8% |

**コンテキストは生のトークンの 99.2%、コスト加重で 82.9%。出力は生で 0.6%、加重で 16.3%。**

セッションの中央値は、書いた量の **109 倍**のコンテキストを再送していました。348 セッションのうち、書いた量が再送量を上回ったのはわずか **5 件**です。

返答を短くしたり、冠詞を落としたり、原始人のような話し方をしてトークンを節約するスキルはすべて、この **0.6%** を最適化しています。出力トークンの単価が高いことを加味しても、4 項目の中で最も小さいものを狙っていることに変わりはありません ── しかもそれ自身の指示が、毎ターン再送されるコンテキストに永久に追加されるのです。

節約分がいつまでも姿を現さないのは、そのためです。

*（生の割合と加重の割合を両方載せているのは、両者が別の物語を語るからです。生の割合はコンテキストウィンドウを埋めるもの、加重は公開されている課金比率 ── cache write 1.25 倍、cache read 0.10 倍、出力は入力の 5 倍 ── を使ったものです。都合のいい方だけを引用するのが問題そのものであって、解決策ではありません。）*

## 自分の数字で実行する

```bash
git clone https://github.com/xniperbuilds/burnrate
cd burnrate/plugins/burnrate/skills/burnrate/scripts
python burnrate.py --days 30
```

Python 3.8+、標準ライブラリのみ ── pip install 不要、Node 不要、シェルインストーラ不要、`curl | bash` もありません。Windows・macOS・Linux で同じように動作します。

すでにディスク上にあるセッション記録（`~/.claude/projects/**/*.jsonl`）を読み、次を出力します：

- 生とコスト加重のトークン内訳
- どのツールが最も多くの分量をコンテキストに入れているか、その平均結果サイズ
- 何度も繰り返し読んでいるファイル
- 単独でセッションを支配するほど大きいファイル
- 画像とバイナリのペイロード（別集計、かつ正直な扱い）

```
  [HIGH] 5 回以上読まれたファイルが 94 件
      変更されていない同じファイルの再読み込みに、初回以降でおよそ
      240 万トークン（概算）。最悪：project-notes.md（107 回）。
      -> 中身がコンテキストに残らなかったため繰り返し読まれています。

  [HIGH] コンテキストに戻される全分量の 50% が Read によるもの
      3,100 回の呼び出しで合計約 450 万トークン。1 回あたり平均
      1,400 トークン、単一結果の最大は約 16,800 トークン。
      -> ファイル全体ではなく offset/limit で読みましょう。
```

## 何かを入力する前に、何が読み込まれているか

```bash
python burnrate.py --startup
```

起動時コンテキストは**すべてのセッションのすべてのターン**で課金されるため、最初に知るべき最も影響の大きい情報です。実際の出力：

```
-- 実測（各セッションの最初の課金ターン）------------------------
  起動時コンテキストの中央値      60,057 トークン   310 セッション
  これは以降の全ターンで cache_read として再送されます。

-- 帰属（設定をスキャン、概算）----------------------------------
  スキルの description                  8,185  57 スキル
  CLAUDE.md（ユーザー）                  3,674
  メモリ索引（MEMORY.md）                2,758  上限 200 行 / 25KB
  サブエージェントの description         1,258  18 件
  帰属できた合計                        15,875

  帰属不能な残差                        44,182  システムプロンプト + ツール schema
  自分で削れる割合                        26.4%
```

設定ファイルの見積もりツールと違う点が 3 つあります：

- **実測**値は正確です ── 単語数の推定ではなく `usage` フィールドから取得しています。
- **残差**を隠さずに報告します。起動コストの 3 分の 2 はシステムプロンプトとツール schema で、自分のファイルをいくら編集しても変わりません。これを伝えるのは、動かせない数字を最適化しようとするのを防ぐためです。
- スキルとサブエージェントについては **frontmatter のみを計上**します。本文はオンデマンド読み込みなので、スキルファイル全体を数えると ── 設定ディレクトリをスキャンする類のツールがやりがちですが ── 起動コストを何倍にも過大評価してしまいます。

よくある驚き：**インストールしたまま使っていないスキルが `CLAUDE.md` より重い。** 各スキルの description は、呼び出すかどうかに関係なく毎ターン読み込まれます。そこで `--startup` は履歴全体から実際の `Skill` ツール呼び出しを数え、「インストール済み」と「実際に使った」を切り分けます：

```
  履歴全体（416 件の記録。--days の範囲ではありません）：
    インストール 57  |  呼び出し記録あり 12  |  記録なし 45

  呼び出し記録のないスキルに毎ターン約 6,143 トークン。
  100 ターンのセッションなら約 61 万トークンです。
```

これは無駄の見積もりではなく、名前の付いた無駄です。重い順に並びます。設定ディレクトリを走査するだけのツールにこれは分かりません。

## 自分の節約を証明する

```bash
python burnrate.py --snapshot before
#  ... 何かを変更する ...
python burnrate.py --compare before
```

`--compare` は**ターンあたりの平均**を報告するので、忙しかった週が悪化に見えてしまうことはありません：

```
                                             変更前      現在      変化
  cache write（新規コンテキスト）             8.6K       5.9K    -31.7%
  cache read（毎ターン再送）                 213.3K     219.5K      2.9%
  output（エージェントが書いた分）             1.4K       1.4K      1.3%

  コスト加重／ターン                         39.1K      36.4K     -6.9%

  これはあなたが実測した変化です。他の誰かについての主張ではありません。
```

## スキルとしてインストール

```
/plugin marketplace add xniperbuilds/burnrate
/plugin install burnrate@xniperbuilds
```

インストール後は 3 つのことを行います：提案の前にまず測定する。安いほうの 0.6% ではなく高いほうの 83〜99% を狙ったコンテキスト規律を適用する。そして再測定し、改善を主張ではなく事実にする。削減手順の全体 ── 効果順に並び、各削減の代償も明記 ── は [`references/cuts.md`](../../plugins/burnrate/skills/burnrate/references/cuts.md) にあります。

## やらないこと

- **エージェントに奇妙な話し方をさせません。** 電報体の出力は請求のごく一部を削る一方で、結果のレビューを難しくします。
- **平均値を提示しません。** あなたの実測値だけです。
- **自分自身のコストを隠しません。** 呼び出されるとこのスキルファイルもコンテキストに入ります。短いセッションではその分が節約を上回ることがあり、`--compare` はそれを正直に示します。
- **正確さをトークンと引き換えにしません。** 簡潔さが適用されるのは伝送される内容だけで、推論・テスト・コードやエラーの原文には決して適用しません。

## 既知の制約

- トークン総量は `usage` フィールド由来で正確です。ツール結果の分量は約 4 文字/トークンで換算しており、登場箇所すべてで概算と明記しています。
- 画像と PDF は文字数ではなく寸法で課金されます。別集計とし、トークン数には決して変換しません。
- コスト加重はトークン種別間の公開比率であり、モデルごとの価格ではありません ── したがって加重列は割合であって金額ではありません。
- サブスクリプションプランは API 価格と異なる重み付けの可能性があります。そのため生と加重の両方を報告しており、どちらも請求額としては提示していません。
- ローカルのセッション記録しか見えません。別のマシンやブラウザで行った作業は集計されません。
- 上記のデータはある 1 人のヘビーユーザーの 348 セッションです。普遍的な法則ではなく証拠です ── そしてそれこそが要点です。自分のデータで実行してください。
